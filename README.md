# Document Room

A local file metadata index. Python 3.10+ and the standard library are sufficient.

Run `python3 document_room.py add policy.md --tag legal --tag policy` from this directory to index the sample policy. Add the second sample with `python3 document_room.py add meeting.txt --tag operations`. `python3 document_room.py search --tag legal --text policy` returns matching metadata as JSON. Multiple tags are combined with AND; tags are trimmed and lowercase, and text matches the relative path without case sensitivity.

The default document root is `samples`; metadata is persisted in `.state/documents.json`. Override these with `--root` and `--index` before the subcommand. Re-adding a file refreshes its size, SHA-256 and tags. Search reads the stored metadata, not live file contents. Files must resolve inside the document root. This version does not copy documents, extract content or watch filesystem changes. Use the Python `DocumentRoom.add` and `DocumentRoom.search` methods for the same operations. CLI errors return JSON and exit 2.

## Document archiving

`python3 document_room.py archive meeting.txt` flips a registered document into the archived state without touching its file, and `DocumentRoom.set_archived(relative_path, archived)` does the same from Python; pass `--restore` (or `archived=False`) to mark it active again. The positional path matches the index's relative-path key exactly and case-sensitively, exactly as for `refs`: it is never resolved against the filesystem, the file is not parsed, and archiving or restoring works even when the original file has been deleted. The state is stored as a boolean `archived` field on the record; records written before this feature simply lack the field and are treated as active, without the field being added. Restoring stores `archived: false` explicitly. Setting the same state twice returns the identical record, and no other metadata or references change. The updated full record is printed as JSON with exit 0.

The first `add` of a path never stores an `archived` field; re-adding a path that already has the field keeps its archived state along with its references. `search` and `export` (CLI flag `--archive-state`, Python argument `archive_state`) accept only `all`, `active` and `archived`; the default `all` keeps the previous selection unchanged. `active` selects records without a true `archived` field and `archived` only records with `archived: true`, in conjunction with the existing tag and path-text filters. Search still returns the complete stored records sorted by path without filling in a default field; export keeps the same document fields, five file statuses and `complete` rule.

With reference expansion (`export --with-references`), the archive filter only chooses the starting documents: every referenced document is pulled in recursively regardless of its archive state, each path still appears once and cycles still terminate. For example, an active `policy.md` that references an archived `meeting.txt` still produces a manifest containing both under `--archive-state active --with-references`.

Archiving only modifies the index; searching only reads stored metadata; exporting keeps its live file checks and never writes a manifest. Setting the archive state, or filtering with a state other than `all`, validates the whole index: invalid JSON or UTF-8, malformed record structures, references that are not lists of strings or point at unregistered paths, and a non-boolean `archived` field all raise `ValueError`, even when the bad record is not selected. A non-string or unregistered path, a non-boolean `archived`, or a non-string/illegal `archive_state` also raises `ValueError`; index read/write failures raise `OSError`, and failed input validation never changes the index. With no index, setting the state is treated as an unregistered path and creates no file, while filtering returns an empty result (an empty manifest has `complete` false). The CLI prints JSON and exits 0 on success, or a JSON object containing `error` with exit code 2 on these failures.

## Document categories

`python3 document_room.py category policy.md --value "Legal Team"` assigns a single category to a registered document, and `DocumentRoom.set_category(relative_path, category)` does the same from Python; `--value` is required. The positional path matches the index's relative-path key exactly and case-sensitively, exactly as for `archive`: it is never resolved against the filesystem, the file is not parsed, and the category can be changed even when the original file has been deleted. The category must be a string; it is stripped of leading and trailing whitespace and stored as a `category` field, preserving case and any inner whitespace, and the updated full record is printed as JSON with exit 0. An empty (or all-whitespace) value stores `""` and marks the document uncategorized. Records written before this feature simply lack the field and are treated as uncategorized, without the field being added. Setting a category changes nothing else: other metadata, references and the archived state are preserved.

The first `add` of a path never stores a `category` field; re-adding a path that already has one keeps its category along with its references and archived state. `search` and `export` (CLI flag `--category`, Python argument `category`) accept an optional category filter: omitting it or passing `None` keeps the previous selection unchanged, while an explicit empty string selects only uncategorized records. Both the stored category and the filter value are stripped of surrounding whitespace and then compared as full case-sensitive strings, in conjunction with the existing tag, path-text and archive filters. Search still returns the complete stored records sorted by path; export keeps the same document fields, five file statuses and `complete` rule, and the category filter only chooses the starting documents — with `--with-references` every referenced document is pulled in recursively regardless of its category, with the usual dedup, cycle termination and `complete` rules.

Setting a category, or filtering with a category other than `None`, validates the whole index: invalid JSON or UTF-8, malformed record structures, references that are not lists of strings or point at unregistered paths, a non-boolean `archived` field, and a stored `category` that is not a string all raise `ValueError`, even when the bad record is not selected. A non-string category, a non-string or unregistered path, or a filter value that is neither a string nor `None` also raises `ValueError`; index read/write failures raise `OSError`, and failed input validation never changes the index. With no index, setting a category is treated as an unregistered path and creates no file, while filtering returns an empty result. The CLI prints JSON and exits 0 on success, or a JSON object containing `error` with exit code 2 on these failures.

## Version notes

`python3 document_room.py note policy.md --value "v2 draft"` attaches a free-form version note to a registered document, and `DocumentRoom.set_version_note(relative_path, note)` does the same from Python; `--value` is required. The positional path matches the index's relative-path key exactly and case-sensitively, exactly as for `refs`: it is never resolved against the filesystem, the file is not parsed, and the note can be changed even when the original file has been deleted. The note must be a string; it is stripped of leading and trailing whitespace and stored as a `version_note` field, preserving case, inner whitespace and newlines, and the updated full record is printed as JSON with exit 0. An empty (or all-whitespace) value stores `""` and clears the note. Records written before this feature simply lack the field and are treated as having no note, without the field being added. Setting a note changes nothing else: other metadata, references, the archived state and the category are preserved.

The first `add` of a path never stores a `version_note` field; re-adding a path that already has one keeps its note along with its references, archived state and category. `search` and `dump` return the stored note alongside the other metadata exactly as saved. `python3 document_room.py export --release "Q4 Launch" --with-version-notes` (or `export_manifest(..., include_version_notes=False)` with the flag on — the parameter is new, defaults to off, and the original parameter positions are unchanged) adds a `version_note` field to every manifest document: records without a stored note export `""`, and documents pulled in by reference expansion carry their own note. With the flag off no `version_note` field is added. Notes never participate in filtering, reference expansion, origin annotation, sorting, the five file statuses or the `complete` rule, and by default `compare` preserves the field in returned documents without comparing it (see the optional version-note comparison below).

Setting a note, or exporting with notes enabled, validates the whole index: invalid JSON or UTF-8, malformed record structures or field types, references that are not lists of strings or point at unregistered paths, and a stored `version_note` that is not a string all raise `ValueError`, even when the bad record is not selected. A non-string path or note, an unregistered path, or a non-boolean `include_version_notes` also raises `ValueError`; index read/write failures raise `OSError`, and failed input validation never changes the index. With no index, setting a note is treated as an unregistered path and creates no file, while a noted export returns an empty manifest with `complete` false. The CLI prints JSON and exits 0 on success, or a JSON object containing `error` with exit code 2 on these failures. Import keeps its existing conflict rules and extra-field preservation, and exporting never writes a manifest file or modifies the index or the original documents.

## Release manifests

`python3 document_room.py export --release "Q4 Launch" --tag legal --text policy` checks a release against the live files and prints `{"release", "complete", "documents"}`. The release name is required and trimmed; blank or non-string names raise `ValueError` from `DocumentRoom.export_manifest` (the CLI prints a JSON error and exits 2). `--tag` (repeatable, AND-combined) and `--text` (case-insensitive path substring) filter records with the same normalization as `search`. Documents are sorted by recorded relative path and keep their stored `path`, `name`, `bytes`, `sha256` and `tags`, plus a `status`:

- `ready` — present, and both byte count and SHA-256 match the index;
- `changed` — present but the size or digest differs;
- `missing` — absent, a dangling symlink, or now a directory;
- `unsafe` — the resolved path escapes the document root (the target is never read);
- `unreadable` — any other resolution or read failure.

Stored metadata is never overwritten with current values, and one document failing does not stop the others. `complete` is true only when the manifest is non-empty and every document is `ready`; an empty manifest still contains all three top-level fields. A missing index yields an empty manifest and is not created; malformed JSON or records whose structure/types do not match the registered format raise `ValueError`, and read failures raise `OSError`. Exporting only reads the index and files: it never copies documents, writes a manifest file or updates the index.

## References

`python3 document_room.py refs policy.md --to meeting.txt` records that a registered document directly refers to other registered documents, and `DocumentRoom.set_references(relative_path, targets)` does the same from Python. The source path is the positional argument and `--to` is repeatable; omitting `--to` clears the references. Paths match the index's relative-path keys exactly (case-sensitive) and are never resolved against the filesystem. Targets are deduplicated, sorted by path and stored as a `references` array on the record — an empty list is stored as `[]`. Self-references and mutual references are allowed. The updated record is returned as JSON and the CLI exits 0.

A non-string source, an unregistered source or target, or targets that are not a list of strings raise `ValueError` without changing the index; a missing index is treated as empty and is not created. Corrupt JSON, records that do not match the registered format, a stored `references` field that is not a list of strings, or a stored reference to an unregistered path also raise `ValueError`, and index read/write failures raise `OSError`. Records written before this feature have no `references` field and are treated as having none: the first `add` of a path stores only the original fields, re-adding the same path keeps its references, and `search` returns any saved references alongside the other metadata.

`python3 document_room.py export --release "Q4 Launch" --with-references` (or `export_manifest(..., include_references=True)`) expands the manifest: the usual tag and text filters pick the starting documents, then every referenced document is pulled in recursively — references are included whether or not they match the filters, each path appears once, and cycles still terminate. The manifest keeps the existing top-level and document fields sorted by path, every listed file is checked with the same status rules, and `complete` is false when any document is not `ready` or the manifest is empty. Reference-aware exports validate stored references as above; without the flag, export behaves exactly as before.

## Reference origins

`python3 document_room.py export --release "Q4 Launch" --with-references --with-origins` (or `export_manifest(..., include_references=True, include_origins=True)`) additionally records why each document entered the manifest. The option is off by default and requires reference expansion: a non-boolean `include_origins`, or enabling it without `include_references`, raises `ValueError`. Without the flag, export behaves exactly as before and no `origins` field is added.

With origins enabled, every document gains an `origins` array whose entries are `{"path", "distance"}` objects: `path` is the registered path of a starting document (one selected by the tag, path-text, archive and category filters) and `distance` is the minimum number of reference edges from that starting document to this one, following the reference direction. Each reachable starting source appears at most once per document, a starting document lists itself with distance 0, shared documents keep every starting source, multiple routes collapse to the shortest distance, and self-references and cycles still terminate. `origins` is sorted by source path in case-sensitive lexicographic order, while `documents` keeps its usual path ordering. For example, with `a.md` and `b.md` selected, `a.md` referencing `c.md` directly and `b.md` reaching `c.md` through `d.md`, `c.md` lists `a.md` at distance 1 and `b.md` at distance 2 while `d.md` lists only `b.md`; if `c.md` also references `a.md`, then `a.md` additionally lists `b.md` at distance 3.

Each document still appears once, an empty selection still yields an empty manifest with `complete` false, and the five file statuses and `complete` rule are unchanged. Enabling origins validates the whole index like reference expansion does — invalid JSON or UTF-8, malformed record structures or field types, and references that are not lists of strings or point at unregistered paths raise `ValueError` even when the bad record is not selected, and index read failures raise `OSError`. Exporting remains read-only: it never writes a manifest file or updates the index, and a missing index is treated as empty without being created. `compare` preserves the `origins` field in returned documents like any other extra field and never compares it.

## Reference impact

`python3 document_room.py impact meeting.txt` answers the reverse question — which registered documents use a given document — and `DocumentRoom.reference_impact(target, transitive=False, include_routes=False)` does the same from Python. The positional path identifies the target with the same exact, case-sensitive relative-path key as `refs`; it is never resolved against the filesystem. By default only direct referrers are returned; pass `--transitive` (or `transitive=True`) to also include every document that reaches the target through one or more reference edges. The command prints `{"path", "documents"}` and exits 0, where `path` echoes the input key.

Each document is the same record `search` returns plus an integer `distance`: the minimum number of reference edges from that document to the target. Direct referrers always have distance 1; transitive results add documents at greater distances. Results are sorted by distance ascending and then by relative path lexicographically, each path appears once, and the target itself is always excluded even when it references itself. Self-references and reference cycles stay legal and the query always terminates. A registered target that nobody references yields an empty `documents` array.

Pass `--with-routes` (or `include_routes=True`) to also attach a `route` array to each document: one shortest reference chain explaining how that document depends on the target, starting at the referrer's own path and following registered references down to the target, so its length minus one equals `distance`. When several equally short chains exist, the one whose full path array is smallest in case-sensitive lexicographic order is shown, regardless of index or `references` ordering. Routes never repeat a path, and without the flag no `route` field is added; the result set, distances and ordering are unchanged either way.

The impact query reads the stored index only: missing, changed or unreadable document files do not affect the result and no live file state is checked, and the index is never modified or created. A non-string or unregistered target, or a non-boolean `transitive` or `include_routes`, raises `ValueError`; a missing index is treated as empty (so any target is unregistered and no file is created). Corrupt JSON, records that do not match the registered format, a `references` field that is not a list of strings, or a reference to an unregistered path also raises `ValueError` — even when the offending record is unrelated to the target — and index read failures raise `OSError`. The CLI reports these as a JSON object with an `error` field and exit code 2. Old records without a `references` field are treated as having none, and the field is not added.

## Duplicate registration query

`python3 document_room.py duplicates --tag release --text docs` finds registered documents whose stored contents coincide, and `DocumentRoom.find_duplicates(tags=(), text="")` does the same from Python; both paths give identical results. `--tag` is repeatable and `--text` takes one value, both filtered with the same normalization as `search` (tags are trimmed, lowercased, empty tags ignored and combined with AND; text matches the relative path case-insensitively). With no filter every record is considered.

Two records are duplicates only when both stored `bytes` and stored `sha256` are equal — the digest is compared as the exact stored string — and a group needs at least two distinct paths. `name`, `tags` and `references` never participate in the judgement, so same-named records with different contents are not grouped. The result is `{"groups": []}` when there are no duplicates or no group has a member the filter matches.

Each group is `{"bytes", "sha256", "matched", "documents"}`: `matched` lists the paths of members that satisfy the filter, `documents` lists the group's full stored records from the whole index (with whatever fields were stored, including `references` when present; neither `references` nor `status` is added). Both arrays are sorted by path and contain each path once, and the groups themselves are sorted by the smallest member path. A filter hitting any single member returns the entire group: querying the `release` tag when only `a.txt` of two identical small files (`a.txt`, `b.txt`) carries it still returns both records, with `matched` listing just `a.txt`.

The query reads the stored index only: modifying, deleting or replacing an original file with an escaping symlink does not change the result or the index, and a missing index yields empty groups without creating a file. The Python `tags` argument must be a list or tuple of strings and `text` a string, otherwise `ValueError` is raised. Invalid JSON or UTF-8, records not matching the registered format, a `references` field that is not a list of strings, or a reference to an unregistered path also raise `ValueError` — even when the offending record is not in a returned group — and index read failures raise `OSError`. The CLI prints JSON and exits 0 on success, or an object with an `error` field and exit code 2 on failure.

## Metadata import

`python3 document_room.py import --from records.json` merges a batch of registrations from another index into the current one, and `DocumentRoom.import_records(batch)` does the same from Python with the decoded dictionary; both paths give identical results. The source is a UTF-8 JSON object mapping each relative-path key to a complete record whose `path` equals the key — the same shape as the stored index. Importing only copies metadata: document files are never read or copied, so records register fine while their files are missing.

Records are stored exactly as given: paths, tags and categories are not normalized, optional fields (`references`, `archived`, `category`) are not added, and any extra JSON fields are preserved. A successful import returns `{"added", "unchanged"}` — the paths this batch newly registered and the input paths that already existed with identical records — each sorted by path in case-sensitive lexicographic order, and the CLI prints it as JSON and exits 0.

A path already registered counts as unchanged only when the existing and incoming records have exactly the same field set and values: array order matters, object key order does not, and a missing optional field differs from its explicit default. A same-path record with different data fails the whole batch with `ValueError` and nothing is overwritten. Both the batch and the merged index are validated against the registered format — required field types, `bytes` as a non-boolean integer, and the optional `references`, `archived` and `category` types — so a malformed record fails the import even when its path is not part of the batch. Every reference target must be registered in the union of the existing index and the batch; forward references within the batch, self-references and cycles are allowed, and an unregistered target fails the whole batch with `ValueError`.

A non-object batch, invalid structure or field types, a key that does not match its record's `path`, and corrupt JSON or UTF-8 in the source file raise `ValueError`; reading the source file or the index and writing the index raise `OSError`. Any failure leaves the source file and the existing index untouched and registers nothing. A missing index is treated as empty; an empty batch or a batch whose records are all identical to the stored ones neither writes nor creates the index. After an import, `search` returns the full stored records and `export` keeps its five statuses, origin annotation and `complete` rule.

## Metadata snapshot export

`python3 document_room.py dump --tag legal --text policy` prints a metadata snapshot of the selected records as a JSON object mapping each relative-path key to its complete stored record — the same shape `import` accepts — and `DocumentRoom.export_records(tags=(), text="", archive_state="all", category=None)` does the same from Python; both paths give identical results. The command uses the global `--root` and `--index` options, prints only the JSON object with no wrapper and no file statuses, and exits 0. The snapshot can be saved and merged into another (empty) index with `import --from`.

`--tag` (repeatable, AND-combined), `--text` (case-insensitive path substring), `--archive-state` and `--category` filter with the same semantics as `search`, and with no filter every record is a starting document. The filters only choose the starting documents: every referenced document is then pulled in recursively along the reference direction regardless of the filters — archived or deleted files included — each path appears once, and self-references and cycles terminate. Documents that merely reference a selected one are not included. Records are returned exactly as stored: extra JSON fields are preserved, array order, duplicate elements, case and whitespace are untouched, and missing optional fields are not filled in. The object is keyed by path in case-sensitive lexicographic order.

The whole index is validated before the result is returned: invalid JSON or UTF-8, records that do not match the registered format, and references that are not lists of strings or point at unregistered paths raise `ValueError` even when the bad record is not selected. A `tags` argument that is not a list or tuple of strings, a non-string `text`, an illegal `archive_state`, or a `category` that is neither a string nor `None` also raises `ValueError`; index read failures raise `OSError`. The CLI reports these as a JSON object with an `error` field and exit code 2, printing no partial snapshot. A missing index or an empty selection yields an empty object and creates no file. Dumping is read-only: it never reads or copies the original documents, never writes a snapshot file, and never modifies the index.

## Registration removal

`python3 document_room.py remove meeting.txt` unregisters a single document's metadata record, and `DocumentRoom.remove_record(relative_path, detach=False)` does the same from Python. The positional path matches the index's relative-path key exactly and case-sensitively, exactly as for `refs` and `archive`: it is never resolved against the filesystem, the document file is never read, moved or deleted, and removal works even when the original file has already been deleted. Only the index changes: no other registrations are recursively removed along reference edges.

By default the operation is blocked with a `ValueError` whenever any *other* record's `references` contains the target path, and the index is left completely unchanged; the target's reference to itself never blocks its own removal. Records that merely reference one another transitively, without a direct edge to the target, do not block it. Pass `--detach` (or `detach=True`) to first remove every occurrence of the target from all other records' `references` and then remove the target's registration. Detaching preserves the order and any duplicate entries of the surviving references, never adds a `references` field to a record that lacked one, and stores `[]` on a record whose references all pointed at the target; every other field and every unaffected record keeps its stored value.

A successful removal returns `{"removed", "updated"}`: `removed` is the target's complete record exactly as stored before the removal, and `updated` is an array of the complete records whose references were actually cleaned, sorted by path in case-sensitive lexicographic order — an empty array when nothing referenced the target (the default mode can only succeed in that case). The CLI prints the object as JSON and exits 0. After removal, `search`, `dump` and export operate on the remaining registrations; for example, once a referenced document is detached away, a reference-expanded listing only contains the surviving referrer.

The whole index is validated against the same format `import` accepts before anything changes: a non-string or unregistered path, a non-boolean `detach`, corrupt JSON or UTF-8, malformed record structures or field types, and references that are not lists of strings or point at unregistered paths all raise `ValueError` even when the offending record is unrelated to the target, and failed validation never writes the index. Index read/write failures raise `OSError`. A missing index is treated as an empty room: removing any path is reported as unregistered and no file is created. The CLI prints a JSON object containing `error` with exit code 2 on these failures.

## Registration path migration

`python3 document_room.py relocate meeting.txt docs/meeting.txt` moves a document's registration to a new path after you have moved the file yourself, keeping the original registration and every reference relationship, and `DocumentRoom.relocate_record(source, destination)` does the same from Python. The command uses the global `--root` and `--index` options and takes the old path first and the new path second. It only rewrites the stored index: document files are never moved, copied or deleted.

The old path matches an index relative-path key exactly and case-sensitively, exactly as for `refs`, `archive` and `remove`: it is never resolved or read against the filesystem, so the migration works even when the original file has already been deleted. The new path follows the same resolution as `add` — joined under the document root, resolved, and stored as the canonical forward-slash relative path of the actual file (for example `docs/meeting.txt`, never with a `./` prefix). The target must exist and be a file inside the root; a target that resolves outside the root is rejected without being read, as are dangling links, symlink loops and paths that resolve outside the root. When either the target's byte count or its SHA-256 differs from the original registration, `ValueError` is raised and the content metadata is not refreshed; bytes, digest, tags and every other stored field keep their registered values rather than being updated from the new file.

On success the old index key is replaced by the new canonical key. The moved record's `path` becomes the canonical new path and its `name` the target file's name; `bytes`, `sha256`, `tags` and every other field keep their values, and optional fields that were absent stay absent. Every `references` array in the index that contains the old key is rewritten to use the new key, including the moved record's own self-reference. Rewriting preserves array order and duplicate entries, never adds a `references` field to a record that lacked one, and self-references and reference cycles stay legal. For example, with `policy.md` referencing `meeting.txt`, moving the latter to `docs/meeting.txt` makes both the stored reference and the reference-expanded manifest listing use the new key.

The result is `{"before", "after", "updated"}`: `before` is the moved record's complete record as stored before the migration (with the old path and name), `after` is its complete record after the migration, and `updated` lists only the *other* complete records whose references were actually replaced, sorted by path in case-sensitive lexicographic order — an empty array when nothing else referenced the old key. The CLI prints the object as JSON and exits 0.

After a migration, `search`, `dump`, `impact`, `duplicates`, reference expansion, origin annotation and manifest export all use the new key; existing entry points, tag/text/archive/category filter semantics, the five file statuses and the `complete` rule are unchanged.

The whole index is validated against the same format `import` accepts before anything changes — record structure, the public optional field types (`references`, `archived`, `category`, `version_note`) and every reference target — so corrupt JSON or UTF-8, malformed records or field types, and dangling references all raise `ValueError` even when the bad record is unrelated to the migration; any failed validation leaves the index bytes exactly as they were. A non-string source or destination, an unregistered old key, a destination canonical key that is already registered (including when it equals the old key), a missing or non-file target, a target resolving outside the root, or a symlink loop also raises `ValueError`. File or index read/write failures raise `OSError`. A missing index is treated as an unregistered old key and creates no file. The CLI prints a JSON object containing `error` with exit code 2 on these failures.

## Batch tag editing

`python3 document_room.py tags policy.md meeting.txt --add legal --add release --remove draft` edits the stored tags of one or more registered documents in a single batch, and `DocumentRoom.edit_tags(paths, add_tags=(), remove_tags=())` does the same from Python; all three parameters accept only a list or tuple of strings. The command uses the global `--root` and `--index` options and takes one or more positional paths, with repeatable `--add` and `--remove` flags (each may be omitted). Paths match the index's relative-path keys exactly and case-sensitively, exactly as for `refs` and `archive`: they are never resolved against the filesystem, duplicate paths are processed only once, and editing works even when the original files have been deleted, changed or made unreadable — document files are never read or modified.

Both the input tags and each selected record's existing tags use `add`'s normalization: surrounding whitespace is trimmed, letters are lowercased, and empty items are ignored. The resulting tag set is the normalized existing set with `remove_tags` taken out and `add_tags` added, deduplicated and saved in lexicographic order. Adding a tag the record already has and removing a tag it never had are both allowed. If the normalized add and remove sets overlap, `ValueError` is raised and nothing changes. A record counts as updated whenever the stored tags array differs from the result, including changes caused by normalization alone (case, whitespace, duplicates or ordering); otherwise the path is listed as unchanged and its record is not rewritten.

The result is `{"updated", "unchanged"}`: `updated` is an array of the complete updated records and `unchanged` an array of paths, both sorted by path in case-sensitive lexicographic order with each path appearing once. An empty `paths` list returns two empty arrays. Only the selected records' `tags` arrays change: every other field (and the absence of an optional field) is preserved exactly as stored, unselected records are byte-for-byte untouched, and when every selected record is unchanged the index is not written at all. The CLI prints the result as JSON and exits 0.

The whole index is validated against the same format `import` accepts before anything changes: invalid JSON or UTF-8, malformed record structures or public field types (`references`, `archived`, `category`, `version_note`), references that are not lists of strings or point at unregistered paths all raise `ValueError`, even when the bad record is not selected. Parameters with the wrong container or member type, or any path that is not registered (including a case mismatch), also raise `ValueError`; failed validation never writes the index. A missing index is treated as an empty room: non-empty paths fail without creating the file, while an empty path list returns the empty result without creating it. Index read/write failures raise `OSError`. The CLI prints a JSON object containing `error` with exit code 2 on these failures and also when no paths are given.

After an edit, the existing entry points use the new values: `search`, `dump`, `duplicates`, `impact`, reference expansion, origin annotation and manifest export all read the edited tags. `add` keeps its refresh behavior (re-adding a file recomputes bytes, SHA-256 and tags from the file), reference relationships, duplicate grouping, the manifest statuses and `complete` rule, and every other entry point's semantics are unchanged.

## Manifest comparison

`python3 document_room.py compare --before old.json --after new.json` diffs two manifests previously produced by `export` (plain UTF-8 JSON files), and `DocumentRoom.compare_manifests(before, after)` does the same from Python with the manifest dictionaries; both paths give identical results. The comparison relies solely on the manifest snapshots: the inputs and index are never modified, no document files are read, and nothing is created. The two manifests may use the same release name or different filter selections.

The result is `{"before", "after", "added", "removed", "changed", "unchanged"}`. `before` and `after` echo each input's `release` and `complete` (release/complete differences never affect document classification and `complete` is never recomputed). `added` lists complete documents present only in the second manifest and `removed` those present only in the first; `changed` lists `{"path", "before", "after", "fields"}` keeping both full documents plus the changed field names; `unchanged` lists paths with no compared change.

Documents pair by case-sensitive exact `path` (no normalization); only `name`, `bytes`, `sha256`, `tags` and `status` are compared. Tags compare as string sets, ignoring order and duplicates (but not case or whitespace); the other fields compare by value, so a `status`-only change still counts as changed. Extra document fields are preserved in the returned documents but never compared. Each category is sorted by path and `fields` is sorted by field name; each path appears exactly once. Two empty manifests yield four empty categories.

Each input must be an object with a non-blank string `release`, a boolean `complete` and an array `documents`; every document needs string `path`, `name` and `sha256`, a non-boolean integer `bytes`, an array of strings `tags`, and one of the five statuses, with no duplicate paths within a manifest. Extra fields are allowed. Bad structure or types, duplicate paths, invalid statuses, and JSON or UTF-8 decode errors raise `ValueError` (the CLI prints a JSON error and exits 2); unreadable files raise `OSError`.

## Version note comparison

`python3 document_room.py compare --before old.json --after new.json --compare-version-notes` (or `DocumentRoom.compare_manifests(before, after, compare_version_notes=True)` and `DocumentRoom.compare_manifest_files(before_path, after_path, compare_version_notes=True)`) additionally diffs the `version_note` field exported by `--with-version-notes`. The option is off by default — the new parameter is appended after the original ones and defaults to `False` — and without it the result keeps the exact structure and comparison semantics above, notes included among the extra fields that are preserved but never compared or type-checked. A non-boolean flag raises `ValueError`. All three entry points give identical results.

With the flag on, documents still pair by case-sensitive exact `path`, and a differing `version_note` adds `version_note` to the sorted `fields` of a `changed` item — a note-only change yields `fields` of exactly `["version_note"]`. Notes compare as the exact stored strings: case, surrounding whitespace and newlines are all significant, and a missing field is equivalent to an empty string. The returned `before` and `after` documents keep their complete original contents — no empty note is filled in and the inputs are never rewritten. `added` and `removed` keep their original classification, and with `--detect-relocations` also enabled, pairing eligibility still follows the usual content-uniqueness rules while a successfully paired relocation reports any note difference in its `fields`.

Enabling the option also validates the notes: any document in either manifest that explicitly carries a non-string `version_note` — `null` included — raises `ValueError` with no partial result, even when that document appears on only one side or never pairs. Every other comparison rule is unchanged: the release and `complete` echoes, the category sorting, the empty-manifest result, the tag-set comparison, the remaining extra fields staying out of the comparison, and the read-only behavior (only the two manifest snapshots are read; nothing on disk is created or modified). The CLI prints the result JSON and exits 0 on success, or a JSON object containing `error` with exit code 2 on failure.

## Relocation candidate detection

`python3 document_room.py compare --before old.json --after new.json --detect-relocations` (or `DocumentRoom.compare_manifests(before, after, detect_relocations=True)` and `DocumentRoom.compare_manifest_files(before_path, after_path, detect_relocations=True)`) additionally reports likely registration moves between the two manifests. The option is off by default — the new parameter is appended after the original ones and defaults to `False` — and without it the result keeps the exact structure and comparison semantics above; a non-boolean flag raises `ValueError`. All three entry points give identical results.

Detection runs only on the leftover `added` and `removed` documents after the usual case-sensitive exact-path pairing: common paths still classify as `changed` or `unchanged` and never count toward the uniqueness below. Leftover documents group by the stored `bytes` and `sha256` (the digest compares as the exact stored string, case included), and a group merges into one relocation only when it holds exactly one old-path document and exactly one new-path document. A group with several candidates on either side is left untouched in `added` and `removed` — nothing is guessed from names, tags or ordering.

With the flag on, the result gains a `relocated` array whose items are `{"before", "after", "fields"}` with both complete original documents; merged documents are removed from `added` and `removed`, so every document still appears in exactly one category. `fields` always contains `path` plus any of the usual compared fields that differ (`name`, `status`, `tags` and so on — `bytes` and `sha256` are equal by construction), tags still compare as string sets, and extra fields are preserved in the documents but never compared. `relocated` is sorted by the old path then the new path and `fields` by field name, both in case-sensitive lexicographic order, and it is `[]` when no group qualifies. For example, exporting a manifest, moving `meeting.txt` to `docs/minutes.txt`, migrating the registration with `relocate` and exporting again yields exactly one relocated item whose `fields` are `["name", "path"]`, while two same-content leftover old paths keep every record in `removed` and `added`.

Detection changes nothing else: both manifests are still fully validated as above, the release name, `complete`, the file statuses and the export rules keep their meaning, the comparison reads only the two manifest snapshots (never the original files or the index), and neither the inputs nor anything on disk is modified. The CLI prints the result JSON and exits 0 on success, or a JSON object containing `error` with exit code 2 on failure, printing no partial result.
